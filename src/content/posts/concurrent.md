# 操作系统

## 进程、线程有什么区别？为什么协程切换比线程更快？

进程、线程和协程主要区别在于资源管理方式、调度主体以及上下文切换成本。

‼️**进程是操作系统进行资源分配的基本单位**。每个进程都有独立的地址空间、文件描述符、系统资源等，各个进程之间是相互隔离的。如果发生进程切换，操作系统需要保存和恢复大量上下文信息，例如页表、寄存器以及内存映射等，同时涉及用户态和内核态切换，因此进程切换的开销相对较大。

**‼️线程是操作系统调度的基本单位**。一个进程中可以包含多个线程，这些线程共享进程的资源，例如堆内存、全局变量以及文件描述符。但每个线程仍然拥有**独立的栈空间和寄存器上下文等**。因此线程切换时，不需要切换整个进程地址空间，只需要保存和恢复线程上下文，所以比进程切换成本低。但是线程调度仍然由操作系统完成，需要进入内核态，因此仍然存在一定开销。

协程通常由语言运行时或者用户程序负责调度，不需要操作系统直接参与。协程切换时只需要在用户态保存和恢复少量寄存器和栈信息，不需要进行完整的线程切换，也不需要频繁进入内核态，因此上下文切换成本通常比线程更低。

## 阻塞 I/O、非阻塞 I/O、同步 I/O、异步 I/O 分别是什么意思？

I/O 模型主要用于描述应用程序和操作系统之间处理 I/O 请求的方式。其中，阻塞和非阻塞关注的是应用程序发起 I/O 请求时，调用线程是否会等待；同步和异步关注的是 I/O 操作由谁完成，以及完成结果如何通知应用程序。

**阻塞 I/O** 是最简单的一种 I/O 模型。当应用程序调用 `read` 或 `recv` 等接口读取数据时，如果数据还没有准备好，系统调用不会立即返回，而是阻塞当前线程。线程会一直等待数据准备完成，并完成从内核空间到用户空间的数据拷贝之后才返回。因此这种方式实现简单，但是在高并发场景下，一个线程通常只能处理一个阻塞请求，会造成线程资源浪费。

**非阻塞 I/O** 与阻塞 I/O 的区别在于，当应用程序发起 I/O 请求时，如果数据还没有准备好，系统会立即返回，而不会阻塞当前线程。例如调用 `read` 时，如果暂时没有数据，系统会返回类似 `EAGAIN` 的状态。应用程序需要主动再次尝试读取，或者结合 I/O 多路复用机制等待事件通知。因此非阻塞 I/O 可以避免线程一直等待，但是如果单纯通过轮询检查状态，会造成 CPU 资源浪费。

**同步 I/O** 指的是应用程序需要主动参与 I/O 完成过程，并等待 I/O 操作完成。也就是说，从数据准备、数据从内核空间复制到用户空间，到最终返回结果，调用方都需要等待。常见的阻塞 I/O、非阻塞 I/O 以及基于 epoll 的 I/O 多路复用，都属于同步 I/O 模型，因为==最终的数据处理仍然需要应用程序主动获取结果==。

**异步 I/O** 则不同。应用程序提交 I/O 请求之后可以立即返回，不需要等待 I/O 完成。后续由操作系统负责完成数据准备和数据拷贝，完成之后通过回调、事件通知等方式通知应用程序。因此异步 I/O 可以让应用程序在等待 I/O 的过程中继续执行其他任务，但实现复杂度也更高。

在 Linux 高并发网络编程中，常见方案是非阻塞 I/O 配合 I/O 多路复用，例如 epoll。它允许一个线程同时监听大量连接，当某个连接有数据可读或可写时，操作系统通知应用程序处理。Go 的网络模型底层也是基于类似机制实现的，通过 runtime 的 netpoll 结合 epoll、kqueue 等事件通知机制，实现大量 goroutine 的高并发网络处理。

# Golang 并发

## 为什么 Golang 适合高并发场景

Go 适合高并发场景主要是因为它提供了轻量级并发模型、高效的调度机制以及完善的网络编程支持。

首先，Go 使用 goroutine 作为并发执行单位。相比传统线程，goroutine 的创建成本更低，初始栈空间较小，并且由 Go runtime 管理，不需要完全依赖操作系统线程调度。因此在需要创建大量并发任务时，可以支持比线程模型更高的并发规模。

其次，Go runtime 提供了 GMP 调度模型，对 goroutine 进行用户态调度。其中：G 表示 goroutine；M 表示操作系统线程；P 表示调度资源。

runtime 会负责将大量 goroutine 调度到少量操作系统线程上执行，通过用户态调度减少线程切换开销，并提高 CPU 利用率。

在运行时，M 必须绑定一个 P 才能执行 Goroutine。每个 P 内部都会维护一个本地的 Goroutine 队列。==当线程开始执行任务时，会优先从自己绑定的 P 的本地队列中取 Goroutine 来运行；如果本地队列为空，就会去**全局队列**拿任务；如果全局队列也没有，就会从其他 P 的队列中**偷取一半任务（work stealing）** 来执行，这样可以提高并发性能，加快执行速度。==

第三，Go 对网络 I/O 有较好的支持。Go 的网络模型底层结合了操作系统的 I/O 多路复用机制，例如 Linux 下的 epoll。当 goroutine 进行网络 I/O 阻塞时，runtime 可以将当前 goroutine 挂起，让线程继续执行其他 goroutine，等 I/O 就绪后再恢复执行。因此可以用较少的线程处理大量网络连接。

因此 Go 特别适合网络服务、微服务、RPC 服务等高并发场景。

# 数据存储

## 在缓存一致性场景中，为什么通常建议先更新数据库再删除缓存？

原因是如果先删除缓存，再更新数据库，在并发情况下可能出现缓存重新写入旧数据的问题。

例如：

1. 线程 A 删除 Redis 缓存。
2. 此时线程 B 读取数据，发现缓存不存在，于是查询数据库。
3. 由于线程 A 还没有完成数据库更新，线程 B 读取到的还是旧数据，并将旧数据重新写入缓存。
最终导致缓存中的数据仍然是旧数据。

另外，不推荐直接采用“更新数据库后更新缓存”的方式，因为并发情况下可能出现缓存覆盖问题。

例如：

1. 线程 A 将数据库更新为 V1；
2. 线程 B 将数据库更新为 V2；
3. 线程 B 先更新缓存为 V2；
4. 线程 A 后更新缓存为 V1。

最终数据库中的数据是 V2，但缓存中保存的是 V1，造成数据不一致。

因此常见设计是：更新数据时采用“先更新数据库，再删除缓存”，并通过重试、异步补偿等机制保证最终一致性。

# 数据安全

## 悲观锁和乐观锁的思想分别是什么？

锁的设计核心其实就是解决并发情况下的数据一致性问题。

悲观锁的思路是“先假设一定会发生冲突”，所以在操作数据之前先把锁加上，别人必须等锁释放才能继续操作。这种方式适合**写操作比较多、冲突概率比较高**的场景。

乐观锁的思路正好相反，它假设冲突不会经常发生，所以不会提前加锁，而是在更新数据时再去校验，比如通过**版本号或者时间戳**判断数据是否被修改过。如果发现版本不一致就说明发生了并发冲突，需要重试。像很多库存扣减、CAS 操作其实都是乐观锁思想，比较适合**读多写少**的场景。

## Redis 怎么实现分布式锁？

分布式锁主要用于解决分布式系统中多个服务实例同时访问共享资源时的数据一致性问题。Redis 实现分布式锁的核心思路是利用 Redis 的原子写入能力。

加锁时使用：`SET key value NX EX time`

NX 表示只有 Key 不存在时才能创建，保证同一时间只有一个客户端能够获取锁；
EX 设置过期时间，避免服务宕机后锁永久占用；
value 通常保存当前线程或者请求唯一 ID，用于标识锁的持有者。

例如：

客户端 A：`SET lock:order 12345 NX EX 30`，返回成功，表示获取锁。
客户端 B：`SET lock:order 67890 NX EX 30`，因为 Key 已经存在，所以获取失败，需要等待或者重试。

释放锁时不能直接执行：`DEL lock:order`，因为可能出现误删问题。

1. 假设客户端 A 获取锁，执行任务过程中因为网络问题超过过期时间。
2. Redis 自动删除锁。客户端 B 获取到了新的锁。
3. 此时客户端 A 执行 DEL，会把客户端 B 的锁删除。

因此释放锁时需要先判断锁是不是自己持有。

通常通过 Lua 脚本保证判断和删除的原子性：
```lua
# 只有 value 匹配当前客户端 ID 时，才允许删除
if redis.call("get", KEYS[1]) == ARGV[1]
then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

## 在分布式系统中，CAP 定理和 BASE 理论分别是什么意思？

CAP 指的是 **Consistency（一致性）、Availability（可用性）和 Partition Tolerance（分区容忍性）**。CAP 定理指出，在发生网络分区的情况下，一个系统最多只能同时满足其中两个特性。
在实际的分布式环境中，**网络分区几乎是不可避免的**，所以大多数系统都会默认必须保证分区容忍性。因此在系统设计时通常需要在**一致性 C 和可用性 A 之间做取舍**。

在工程实践中，人们提出了 **BASE 理论**，它是对 CAP 的一种工程化补充。BASE 包括三个概念：**基本可用（Basically Available）、软状态（Soft State）和最终一致性（Eventually Consistent）**。也就是说系统在短时间内可以出现不一致，但最终会达到一致状态。
